# 毫芒 Hairline｜可解释 Agent 决策工作台设计方案

版本：设计草案 v2，2026-10-14

## 1. 页面定位

工作台要回答的是：**模型提供了哪些证据、证据是否可信、系统为何选择当前路径、何时交给人确认**。

```text
模型提供异常和定位证据
  → 校验与路由层检查来源、一致性、分数和规则
  → 工作台呈现证据、原因码、路径及人工交接
```

创新表达是工业质检决策透明化，而非仅展示图片和缺陷框。前端不自行判断缺陷，不改写模型原判，不执行产线放行或返工。

### 当前能力边界

| 能力 | 当前状态 | 展示口径 |
|---|---|---|
| 检测结果契约、四档字段和多类分数 | 已定义草案，真实模型输出待确认 | 演示值明确标注为合成或模拟 |
| `DetectorAgent`、结构校验、确定性路由 | 本地代码已实现 | 可展示本地结构化输出及原因码 |
| 冲突检查、边界分流、Replay、Trace | 本地代码已实现 | 证明流程逻辑，不当作模型成绩 |
| AgentArts 角色配置、工具调用与交接 | 待平台验证 | 真实平台 Trace 到手后再展示为运行证据 |
| 真实视觉模型、四档分级与分数校准 | 待接入和实测 | 不声称已具备可靠识别或分级能力 |
| 人工复核记录服务 | 待实现 | MVP 只做复核入口及交接信息 |

当前路由是**基于证据的确定性规则**。界面出现 `DetectorAgent`、`ValidationAgent`、`RoutingEngine` 名称，不足以证明多 Agent 自主协作。AgentArts 接入后，应以独立角色配置、工具调用、交接数据和平台 Trace 证明其能力；若平台只支持固定流程，就称为多角色工作流。

## 2. MVP 范围与布局

只做一个任务工作台：图像与证据、决策卡、执行 Trace、人工复核入口。批次管理、历史检索、系统设置、独立评测页和完整复核中心后置。

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 样本信息                         DEMO MODE / Synthetic Evidence（右上角） │
├──────────────────────────────────────────────────────────────────────────┤
│ MODEL EVIDENCE → EVIDENCE CHECK → AGENT ROUTING → HUMAN IN LOOP         │
├──────────────────────┬─────────────────────────┬─────────────────────────┤
│ 图像或合成证据示意   │ 校验检查项与结果        │ 纵向本地 Trace          │
│ 分层证据与缺陷记录   │ 建议路径、原因与证据对照│ 输入、发现、输出        │
│                      │ 人工交接说明            │                         │
├──────────────────────┴─────────────────────────┴─────────────────────────┤
│ 来源、模型版本、校准版本、规则版本缺失情况                             │
└──────────────────────────────────────────────────────────────────────────┘
```

视觉中心是中央的“可信校验 → 路径解释”，Trace 保持在第一屏。颜色区分正常候选、待复核和阻塞，但不把颜色本身当作结论证据。

### 顶部状态和模拟标识

显示 `sample_id`、任务状态、`decision_scope`、`demo_only`、`image_analyzed`。`run_id` 只有后端实际产生时才显示；当前 `main.py` 没有此字段，不应伪造。

当 `demo_only=true` 或 `decision_scope=SIMULATION_PREVIEW` 时，在决策卡和图片旁持续显示：

> 模拟预览：该输出未分析当前图片，不能用于真实质量判断或模型成绩。

本地图片上传仅用于浏览器预览。当前模拟检测器不读取图片，上传动作不得造成“已分析该图片”的暗示。

### 图像与缺陷区

显示原图、缺陷框、编号、类别和严重度。没有与当前图片绑定的可信定位结果时，显示明确标为“合成证据示意”的晶圆图形；示意标记不按原图坐标绘制，也不宣称模型看过这张图。只有导入的聚合对象声明图像与检测证据绑定，且提供尺寸和可加载图片时，页面才叠加缺陷框及可加载的掩码。缺陷列表与标注联动属于后续交互增强。

四档颜色仅表达字段，不代表真实严重度模型已接入：`Acceptable` 绿、`Marginal NG` 黄、`NG` 橙、`Gross NG` 红。`Acceptable` 不等于获准放行。

### 决策卡

优先展示路径、证据和原因，而不是单个置信度或一段自由文本：

```text
路径：REVIEW（人工复核）
发现：严重度前两档概率接近
原因码：SEVERITY_BOUNDARY
下一步：核对缺陷边界区域
范围：SIMULATION_PREVIEW；不可用于真实处置
```

路径名称与当前 `routing_engine.py` 保持一致：`NORMAL`（正常候选）、`SUGGESTION`（缺陷处置建议）、`REVIEW`（需要复核）、`FAILED`（无有效建议）。`NORMAL` 和 `SUGGESTION` 都不是产线动作。模拟预览即使出现前三种路径，也须同时显示实际验证路径和不可用于生产的标记。

## 3. 分层证据与可信度检查

不能用一个 `confidence: 95%` 概括全部结论：

| 字段 | 页面名称 | 范围 | 呈现方式 |
|---|---|---|---|
| `defect_probability` | 图像存在缺陷的概率 | 图像级 | 与缺陷列表并列，便于发现冲突 |
| `detection_confidence` | 区域检测分数 | 单缺陷 | 对应缺陷框 |
| `class_confidence` | 缺陷类别分数 | 单缺陷 | 对应类别 |
| `severity_confidence` | 严重度分数 | 单缺陷 | 与四档分布并列 |
| `severity_probabilities` | 四档概率分布 | 单缺陷 | 展示最高档、次高档及差距 |

示意案例可显示异常存在 97%、定位 96%、类别 91%、严重度 52%，因而需要复核。这些数字只能来自标明来源的合成样例。真实模型对分数的定义、校准和映射尚待模型负责人确认。未提供的分数显示“未提供”，不能补零或合并成总置信度。

### 一致性检查

前端展示后端的校验结论和原因码，不在浏览器内建立另一套权威分流规则。典型案例：

```text
模型字段：defect_probability = 0.98；defects = []
一致性检查：失败
原因码：EVIDENCE_CONFLICT
路径：FAILED；无有效处置建议
```

当前 `routing_engine.py` 在缺陷概率达到**原型阈值**而缺陷列表为空时给出 `EVIDENCE_CONFLICT`。`detection_validation.py` 还会拒绝模拟结果、工具错误、字段缺失和非法数值。当前阈值未经真实数据校准，不应称为工业标准。

`FAILED` 时可展开原始工具字段，但不能将冲突输出当作可信标注，也不能继续给出放行或返工建议。

### 版本与审计

模型版本、校准版本和规则版本用于追溯同一图片在不同运行中的结果差异。当前检测契约要求 `model_version`、`calibration_version`；路由输出尚无稳定的 `policy_version`。页面只显示实际返回的版本，缺失时写“未提供/待接入”。真正的审计还需要后端保存输入摘要、时间、版本与人工结论；仅在前端显示版本号不构成审计闭环。

## 4. Trace 如何体现价值

时间线每一步回答：**读取了什么 → 调用或检查了什么 → 发现什么 → 输出什么**。

| 步骤 | 输入或工具 | 关键发现 | 输出 |
|---|---|---|---|
| 检测 | 样本引用、检测工具 | 异常概率及缺陷列表 | 原始结构化检测结果 |
| 校验 | 检测结果 | 来源、字段、分数、坐标是否合法 | `VALID` 或原因码 |
| 路由 | 已校验结果、原型策略 | 四档差距小或分数不足 | `REVIEW` 及理由 |
| 仲裁 | 规则条目与争议证据 | 待核对问题 | 复核建议；当前待实现 |

`main.py` 目前能输出 `execution_trace`、`decision_scope`、`validated_decision` 和原因码。这是本地程序的结构化记录，不等同于 AgentArts 平台 Trace。现有记录也没有每步时间和耗时，界面不能虚构。接入平台后再按实际输出增加工具调用时间、角色交接和知识引用。

## 5. 人工复核与交接

人工复核是高风险或不确定情形的交接机制：边界档、低分数、结果冲突、工具失败、规则未校准都可能使自动建议不可靠。页面并列展示模型原判、复核原因和需要核对的问题。人工结论将来由后端单独保存，不能覆盖模型原判。

MVP 的“进入复核”只打开当前样本的交接视图，不宣称已有完整工单系统。后续复核服务至少保存 `sample_id`、原始检测结果引用、原因码、复核人、结论、理由和时间。正式放行或返工由授权人员依现场流程确认。

## 6. 当前接口与前端映射

前端 Demo 的聚合数据对象已定义在 [Task 10 Demo 数据协议](../contracts/demo_view_contract_v1.md)。本节保留来源和映射说明；实现时以该版本化协议作为页面输入，不直接拼接多个 Agent 原始输出。

- **本地完整流程**：`main.py` 输出 `path`、`reason_codes`、`evidence`、`decision_scope`、`validated_decision`、`execution_trace`，适合驱动决策工作台原型。
- **HTTP 模拟服务**：`POST /v1/inspect` 或 `/v1/detector` 返回检测结果，`GET /health` 返回服务状态；**不返回完整路由和 Trace**。浏览器实时展示完整本地链路时使用 `workspace_server.py` 提供的 `POST /api/agent-case`，它包装现有 `run_inspection` 并返回聚合对象。不能将单独的 `/v1/inspect` 调用展示成已运行三角色工作流。
- **模拟服务图片输入**：`/v1/inspect` 使用 `image_url`，`/v1/detector` 使用 `image_path`；当前 mock 均不读取图片。
- **真实定位证据**：`workspace_server.py` 还可从固定目录读取已保存的 MVTec bottle 推理记录及预测 mask，返回独立的 [真实图像证据协议](../contracts/baseline_evidence_v1.md)。该基线只有原始异常距离，页面展示 `Agent NOT RUN`，不生成四档分流结论。

建议前端只读视图模型：

```ts
type ViewPath = "NORMAL" | "SUGGESTION" | "REVIEW" | "FAILED";

interface DecisionView {
  sampleId: string;
  path: ViewPath;
  reasonCodes: string[];
  decisionScope: "SIMULATION_PREVIEW" | "VALIDATED_MODEL_OUTPUT" | "REJECTED_MODEL_OUTPUT";
  productionUsable: boolean;
  validationStatus: string;
  evidence: {
    defect_probability: number | null;
    defects: Array<{
      defect_id: string;
      defect_type: string;
      detection_confidence: number;
      class_confidence: number;
      severity: string;
      severity_confidence: number;
      severity_gap: number;
    }>;
  };
  executionTrace: Array<Record<string, unknown>>;
}
```

`bbox_xyxy` 在原始检测结果中，当前 `main.py` 的最终视图输出未携带框坐标；图片叠框需要后端安全提供与该图匹配的原始结果。`policy_version`、`run_id` 和人工复核对象待后续接口确定后加入。

## 7. 开发顺序

1. **本地可解释原型**：使用 `main.py` 的合成样例 JSON，完成单页决策卡、分层证据、Trace 和人工交接视图；每处模拟内容标明来源。
2. **图像与接口绑定**：取得与图片对应的授权检测结果后叠框；通过薄 API 或预生成记录向前端提供检测、校验和路由结果。
3. **真实模型接入**：确认四档输出、分数语义、坐标、版本及校准方法；替换模拟数据并验证版本可追溯性。
4. **AgentArts 与人工闭环**：接入真实角色 Trace、知识引用和复核记录，再开放完整复核流程。

技术选型以简单、可演示为准。可使用 React、TypeScript、Vite 和 SVG 绘制标注；单页 MVP 暂不需要批次管理、图表库或独立状态管理框架。

## 8. 演示与验收

至少准备三条本地流程记录：正常候选、边界复核、工具失败或证据冲突。增加明确缺陷和低分数样例时，也须标注为合成数据。

评委应能从同一页面回答：

1. 结果来自模拟，还是已分析图片的真实模型？
2. 哪个字段支持当前判断？哪个字段存在不确定性或冲突？
3. 规则为何给出 `NORMAL`、`SUGGESTION`、`REVIEW` 或 `FAILED`？
4. 模型、校准和规则版本是否可追溯，缺失版本是否如实标记？
5. 哪些结论需要人工确认，人工结论是否与模型原判分开保存？
6. 展示的 Trace 是本地程序记录还是 AgentArts 平台运行记录？

工作台最终呈现的是**证据到决定的过程**，并清楚交代当前原型与目标系统之间的差距。
